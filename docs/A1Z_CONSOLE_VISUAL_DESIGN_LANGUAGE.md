## 0. 参考边界

本规范参考当前 Apple 桌面设计原则，但 A1Z Console 运行于 Linux / Electron，不声称是原生 macOS 应用，也不逐像素复制系统组件：

- [Designing for macOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-macos/) 强调可调整窗口、高精度指针、键盘，以及在较少嵌套层级中呈现更多内容；
- [Sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars) 建议侧栏在窗口缩小时适应或隐藏，并避免为所有图标指定互相竞争的固定颜色；
- [Materials](https://developer.apple.com/design/human-interface-guidelines/materials) 要求按结构语义选择材质并保证可读性，而不是按材质看起来的颜色选择；
- [Color](https://developer.apple.com/design/human-interface-guidelines/color) 要求颜色语义一致，并同时适配浅色、深色与高对比环境；
- [Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility/) 要求两种外观分别验证文字对比度和可访问性。

A1Z 因此只吸收桌面层面的层级、密度、材质和交互原则。系统交通灯、色值和半透明效果都是跨平台近似，不是 AppKit 动态材质。

## 1. 视觉定位

当前界面采用 **macOS 桌面结构启发的双主题工作台**，不是 iOS 卡片界面，也不是传统工控组态屏。其识别特征是：

1. **连续工作面**：内容区域是完整画布，仅用必要的 1 px 分隔线划分功能，不堆叠卡片。
2. **外壳克制**：无 Logo、无窗口标题、无常驻页面小标题；菜单、导航和窗口控制承担外壳功能。
3. **有限材质**：半透明和模糊只用于标题栏、侧栏、悬浮控件和模态遮罩；内容画布保持纯色。
4. **单一交互色**：蓝色只表达选中、焦点和主要确认；绿、黄、红只表达状态或系统窗口控制。
5. **语义去重**：一个区域只保留一个可见名称。终端、模型等由位置和控件语义已经说明的区域不再重复显示标题。
6. **设置不冒充状态**：设置项表达“已保存的配置”，不使用运行中、已连接或已部署的视觉语义。宿主机 / Docker 选择尤其不能暗示进程已经切换。

### 1.1 必须保持的视觉不变量

- 不新增全局渐变、玻璃高光、彩色阴影或装饰性发光。
- 不用卡片套卡片组织普通功能；优先使用留白、对齐和细分隔线。
- 不给每个区域重复添加“小标题 + 解释 + 状态”三件套。
- 常驻内容面板无圆角、无阴影、无外边距；弹层和紧凑控件才使用圆角。
- 同一作用域最多一个蓝色实心确认动作。
- 颜色不能单独承担状态；状态必须同时有文字、图标、形状或稳定位置。
- 新视觉元素必须同时适配深色和浅色，禁止只为一个主题写硬编码颜色。

## 2. 平台与几何基线

### 2.1 使用场景

| 维度 | 约束 |
| --- | --- |
| 平台 | Linux 桌面 Electron 无边框窗口 |
| 屏幕形状 | 横向矩形 |
| 典型观看距离 | 约 60 cm |
| 缩放 | 使用 CSS px，由 Electron / 操作系统负责 DPI 缩放 |
| 输入方式 | 鼠标或触控板、键盘；拖动用于窗口和 3D 视图 |
| 文字方向 | 当前按 LTR 排布；尚未建立 RTL 基线 |
| 内容优先级 | 主工作区 > 终端与模型 / 相机 > 导航与窗口外壳 |

### 2.2 窗口尺寸

- Electron 默认内容区：`1440 × 900`。
- Electron 强制最小尺寸：`1000 × 680`。
- CSS 安全下限：`900 × 640`；桌面发行版不得依赖这个更小值。
- 响应式断点：窗口宽度 `≤ 1080` 时，侧栏折叠为仅图标模式。
- 视觉回归必须至少覆盖：`1440 × 900` 和 `1000 × 680`，两种主题各一张。

- 当前没有通用 `warning` UI token；新增警告语义时必须同时补充两套主题，而不是临时写橙色。

## 4. 字体与图标

### 4.1 字体族

应用界面统一使用：

```css
-apple-system, BlinkMacSystemFont, "SF Pro Text", "Noto Sans CJK SC",
"Microsoft YaHei", system-ui, sans-serif
```

终端统一使用：

```css
"JetBrains Mono", "Cascadia Code", "Noto Sans Mono", monospace
```

不得打包或伪装未经授权的 Apple 字体。系统缺少 SF Pro 时，按上述回退链选择字体。

### 4.2 当前字号层级

| 角色 | 字号 | 行高 / 字重 | 使用位置 |
| --- | --- | --- | --- |
| 启动助手标题 | 28 px | `1.15` / 600 | 三阶段启动助手的当前任务 |
| 启动助手内容 | 14 px | `1.4` / normal | 检查项、状态与失败处置；默认不设置常驻引导段落 |
| 弹窗标题 | 16 px | `1.2` / 600 | 部署方式等独立设置窗 |
| 主控件标签 | 13 px | normal；选中可 500 | 顶部菜单、导航、选项行、确认按钮 |
| 菜单项 | 12 px | normal | 下拉菜单 |
| 紧凑切换 | 10 px | normal | 模型 / RGB / 深度 |
| 微型状态 | 9 px | normal | 连接状态、模型错误 |
| 终端 | 12 px | `1.25` / normal | xterm 内容 |

规则：

- 同一局部最多同时使用 3 个字号。
- 中文不增加字距；仅模型微型状态允许 `0.04em` 技术性字距。
- 不使用全大写英文小标题制造层级。
- 不用粗体替代布局层级；500 用于选中标签，600 只用于弹窗或真正的一级标题。
- 9–10 px 只保留给短状态和紧凑视图切换，不得用于说明、错误原因或连续阅读文本。

## 5. 间距、边界和形状

### 5.1 间距体系

新增布局优先使用 `4 / 8 / 12 / 16 / 20 / 24 px`。当前实现中的非 4 倍数是紧凑桌面控件的光学校正，只能在对应组件中沿用。

| 数值 | 当前用途 |
| --- | --- |
| 2 px | 三个窗口按钮之间 |
| 3 px | 导航行间距、分段控件内边距 |
| 5 px | 菜单内部留白、菜单文字与箭头间距 |
| 6 px | 状态点与文字、状态浮层纵向内边距 |
| 8 px | 菜单栏左边距、侧栏水平内边距、状态横向内边距 |
| 9 px | 导航图标与文字间距 |
| 10 px | 侧栏顶部、视窗浮控件边距 |
| 12 px | 菜单按钮水平内边距、终端右内边距 |
| 14 px | 弹窗按钮水平内边距、窗口右边距、终端左内边距 |
| 16 px | 弹窗标题下间距 |
| 18 px | 弹窗选项组与底部操作间距 |
| 20 px | 弹窗内容内边距 |

### 5.2 圆角

| 半径 | 组件 |
| --- | --- |
| 6 px | 菜单触发器、菜单项、分段选中项 |
| 7 px | 弹窗“完成”按钮 |
| 8 px | 侧栏导航项 |
| 9 px | 分段控件外壳 |
| 10 px | 菜单弹层、弹窗选项组 |
| 12 px | 启动助手的成组检查、状态与参数区域 |
| 14 px | 模态设置窗口 |
| 20 px | 启动助手的大型步骤符号 |
| 50% / 999 px | 状态点、窗口交通灯、状态胶囊 |

常驻面板圆角为 `0`。新增圆角只能复用表中角色，不允许为相邻组件创造 11、12、13 px 等新层级。

### 5.3 边框与焦点

- 普通分隔线：`1 px solid var(--line-soft)`。
- 弹层边界：`1 px solid var(--line)`。
- 焦点环：`2 px solid var(--accent)`，通常向内偏移 `-3 px`。
- 窗口交通灯焦点环向内偏移 `-6 px`。
- 常驻面板不使用完整四边框，只画结构需要的单边分隔线。

## 6. 材质、模糊和阴影

| 层级 | 参数 | 使用限制 |
| --- | --- | --- |
| 标题栏 | 主题表面 96% 不透明 | 仅窗口顶部 |
| 侧栏 | 主题表面 90% 不透明；`saturate(150%) blur(18px)` | 仅导航层 |
| 小型悬浮控件 | `overlay-background`；`saturate(150%) blur(14px)`；`0 1px 4px shadow` | 状态、分段控件 |
| 模型错误浮层 | `overlay-background`；`blur(5px)` | 非交互短状态 |
| 菜单 | `0 18px 46px shadow-strong` | 只在菜单打开时 |
| 模态窗口 | `0 24px 80px shadow-strong` | 只在阻塞式设置窗口 |
| 模态背景 | 黑色 34%；`blur(4px)` | 仅原生 `dialog` backdrop |
| 启动助手 | 深色黑 84% / 浅色系统灰 86%；`saturate(125%) blur(28px)` | 只覆盖标题栏下方的完整工作区 |
| 常驻内容 | 无模糊、无阴影 | 主工作区、终端、视窗 |

禁止在内容卡片、导航选中项或普通按钮上添加大阴影。模糊只用于帮助理解层级，不用于装饰。

## 7. 组件量化规范

### 7.1 自定义标题栏

- 高度：54 px；底部 1 px `line`。
- 整个空白区域可拖动窗口；菜单和窗口按钮必须声明为不可拖动区域。
- 左侧只保留“设置”和“帮助”，不显示 Logo、产品名或无效菜单。
- 菜单区左内边距 8 px。
- 右侧窗口控制顺序固定为：最小化、最大化 / 还原、关闭。
- 每个窗口按钮命中区：28 × 53 px；间距 2 px；整体右内边距 14 px。
- 交通灯可见圆直径 13 px，1 px 半透明黑边。
- 内部符号默认隐藏，窗口控制组 Hover 或单按钮 Focus 时显示。
- 窗口失焦后，三个圆点统一变为 `inactive-window-control`。

| 状态 | 视觉表达 |
| --- | --- |
| Default | 透明或中性表面，次要文字 |

## 10. 动效原则

常驻应用外壳保持即时反馈；启动助手使用一组局部、克制的任务切换动效：

- 普通按钮的颜色、表面和焦点过渡为 120 ms，按压缩放为 60–80 ms，统一使用 `cubic-bezier(.2,0,0,1)`。
- 按压缩放仅用于直接操作反馈；不为导航、面板或状态添加悬浮位移、弹跳、扫光和循环呼吸。
- 启动遮罩首次进入以 `600 ms` 淡入；任务内容以 `520 ms`、`cubic-bezier(.16,1,.3,1)` 从下方 8 px 淡入；底部控件文字以 380 ms 原位淡入，按钮容器不移动。
- 模型包围盒稳定后以 560 ms 淡入；模型层首次出现使用 1000 ms 从右侧 24 px 归位。页面切换时 J1–J6 使用 1200 ms smootherstep 连续插值，镜头同步平移追踪夹爪中心，同一 WebGL 画布保持不变；首尾速度均为零。
- 三个进度圆点的缩放与颜色过渡为 180–220 ms；圆点之间没有连线。
- Three.js 轨道阻尼、终端光标闪烁和自动检查旋转指示是功能反馈，不属于装饰动效。
- 自动检查旋转指示周期为 800 ms、线性匀速；`prefers-reduced-motion` 下停止旋转。
- CSS 界面动效只改合成友好属性；按钮的颜色变化是局部状态例外。`prefers-reduced-motion` 下关闭页面、模型、控件与圆点过渡，取消按钮按压缩放，并让关节立即到达目标姿态。
- 任何直接操作必须在 100 ms 内给出视觉响应；耗时行为属于运行逻辑规范，不由本文定义。

## 11. 文案与语义密度

- 顶栏不显示 Logo、产品名、当前页面标题或环境标签。
- 左侧导航只显示功能名称，不显示“功能”“导航”等分类小标题。
- 终端与视窗依靠布局和 `aria-label` 命名，不重复显示可见标题。
- 一个操作面只保留一个任务标题、一个必要状态和一个直接动作；标题已经说明任务时，不再追加释义相同的引导段落。
- 按钮优先使用 2–6 个汉字的直接动词，如“继续”“移动”“载入”“重试”，避免把过程说明写进按钮。
- 成功与稳定状态压缩为短状态词，如“在线”“已到达”“连接正常”；不在常驻界面复述服务端如何检查、接管或保持目标。
- 等待过程主要由旋转指示与当前动作标签表达，不逐项播报“检查、提交、等待反馈”等内部阶段。
- 安全信息不能因精简而消失。确认层保留一条具体操作要求；错误同时指出结果或下一步，运动结果不确定时明确提示机械臂可能仍在运动。
- 开发预览属于次要环境信息，保持可见但使用弱化样式，不使用大面积蓝色提示框。
- 瞬时反馈占用固定位置；文字出现和消失不得推动输入项或主要按钮跳动。
- 空状态只保留一个必要图标或图形；没有可行动建议时不显示解释段落。
- 相同名词在一个视觉层级只出现一次。例如固定模型区域由位置和 `aria-label` 命名，不在视窗内重复显示“模型”。
- 菜单只保留真实可用项；“关于”可以保留，其他占位项删除。
- 技术词采用稳定写法：`Docker`、`RGB`、`A1Z`；不混用全角英文或无必要的全大写装饰。

## 13. 可访问性基线与已知缺口

### 13.1 当前必须保持

- 菜单、导航和模态选项使用原生 Button / Dialog 语义。
- 菜单、单选组、当前页面和窗口按钮提供相应 ARIA 属性。
- 菜单和模态框可用 Escape 退出；模态框使用浏览器原生焦点约束。
- 可交互图标必须有可访问名称，纯装饰图标使用 `aria-hidden`。
- 状态不能只靠颜色：检查结果有图标和文字，选择状态有勾选或位置。

### 13.2 不得继续扩散的当前缺口

以下问题是现状记录，不是后续组件可以复制的规范：

- 浅色 `text-secondary` 在白底上的近似对比度为 3.44:1；仅适合非关键短标签。
- `text-tertiary` 对比度较低（深色约 2.27:1、浅色约 1.72:1）；不得承载信息。
- 白字位于当前主题蓝色上约为 3.65:1（深色蓝）和 4.02:1（浅色蓝）；小字号实心按钮需要后续引入高对比色或深色文字方案。
- 菜单高 32 px，是精确指针密度，不满足触屏目标；若支持触摸，必须另建 44 px 以上密度模式。
- 当前使用固定 CSS px，尚未完成大系统字体下的布局验证。

新组件必须达到普通文字 4.5:1、UI 边界 3:1，并提供明确的键盘焦点；不能以“与旧组件一致”为理由重复上述缺口。

后续改动遵循以下顺序：

1. 先确定语义角色，复用现有 token、字号、圆角和间距。
2. 现有 token 无法表达时，先修改两套主题的共享定义，再使用新 token。
3. 新增一个字号、圆角、阴影或状态色时，必须在 PR / commit 说明为何现有层级不足。
4. 不在组件中写主题相关原始色值；交通灯、终端 ANSI 和 Three.js 专用调色板是明确例外。
5. 视觉修改必须同时更新深色、浅色及 1080 px 断点。
6. 有意修改本文量化值时，同一变更中更新文档，避免代码与设计基线分叉。

运行语义：源码构建状态不等于机械臂开发模式。控制台默认连接真机；只有启动命令
显式携带 `--development-mode` 时才允许跳过启动步骤和执行无硬件操作预览，且该
模式必须在 Electron 主进程阻断全部真机遥测及控制命令。

## 15. 视觉回归验收

每次影响 UI 的变更至少完成：

```bash
cd console_v2/frontend
npm run typecheck
npm run build
```

评审清单：

- [ ] 顶栏仍为 54 px，窗口可拖动，窗口按钮可点击。
- [ ] 只有设置和帮助两个一级菜单，且同时只打开一个。
- [ ] 168 / 72 px 两种导航宽度行为正确。
- [ ] 主工作区仍是连续面，不出现无理由的嵌套卡片。
- [ ] 终端和模型区域没有重复标题或多余工具按钮。
- [ ] 新颜色全部有深浅主题 token，且没有装饰性语义色。
- [ ] 选中、连接、错误都不只依靠颜色表达。
- [ ] 弹层圆角、阴影和模糊未扩散到常驻内容。
- [ ] 1000 × 680 下没有重叠、截断或面板覆盖。
- [ ] 键盘能访问新增控件，Focus 可见，Escape 能退出临时层。
- [ ] 新增文字满足对比度要求，且未复制第 13.2 节的已知缺口。
- [ ] UI 配置状态没有被误画成运行、连接或部署完成状态。
- [ ] 启动助手的进度、任务内容与底部动作处于同一内容列，没有分别按全窗口居中。
- [ ] 页面和弹层没有重复的“标题 + 同义引导 + 状态说明”，成功状态没有叙述内部处理过程。
- [ ] 瞬时反馈有稳定占位，状态变化不会造成表单和按钮跳动。
- [ ] 安全确认与错误处置在精简文案后仍完整、具体。
- [ ] 启动助手完整覆盖标题栏下方工作区，底层菜单和内容不可操作。
- [ ] 正式构建没有跳过入口；检查失败不能进入参数步骤或主界面。
- [ ] 启动助手不出现相机、ROS、容器名、CAN 接口、命令或环境路径。
- [ ] 自动检查没有启动运行服务、SDK 或设备控制的副作用。
- [ ] 三个进度圆点相互独立、无连线，并按完成顺序逐个点亮。
- [ ] 三页底部按钮位置和 112 / 96 / 132 × 38 px 尺寸保持不变。
- [ ] 三页模型姿态不同；底座世界变换不变，夹爪中心固定在右侧画布中心，夹爪朝向随 J4–J6 变化。
- [ ] 切换时同一画布连续插值 J1–J6 并平移追踪夹爪，不闪烁或重新加载。
- [ ] 启动遮罩下没有来自主视窗模型的固定假阴影或重影。
- [ ] 模型只由窗口右边界裁切，没有径向蒙版或可见的人造图像边界。

## 16. 一句话评审标准

每个新增视觉元素依次回答：

1. 它是否在表达新的、必要的语义？
2. 现有对齐、留白、文字或分隔线是否已经足够？
3. 它在深色、浅色和 1000 × 680 下是否仍然成立？
4. 去掉颜色和装饰后，状态是否依然可理解？

任何一项答不上来，就继续做减法。
