# A1Z SDK 任务驱动技术规范

本文档定义当前仓库基于 A1Z SDK 实现“给定目标位置，驱动机械臂完成抓取任务”所需的技术边界、系统分层、依赖栈、接口职责、缺失能力和交付要求。

本文档不是操作手册，不描述具体命令、具体点击路径或逐步部署流程，只定义应当建设什么、各层负责什么、哪些能力可以直接复用、哪些能力必须补齐。

## 1. 目标与范围

### 1.1 目标

目标系统应支持以下任务语义：

- 输入一个任务目标，至少包含目标空间位置，推荐同时包含姿态约束、抓取方向、夹爪开合要求、执行容差。
- 系统根据目标生成可执行控制命令。
- 机械臂通过 SDK 完成接近、对位、闭合夹爪、撤离等任务阶段。
- 同一套上位机任务逻辑可在三类后端上运行：
  - 仿真后端
  - mock 后端
  - 真机后端

### 1.2 非目标

以下内容不属于当前 SDK 直接保证的范围：

- 自动物体检测
- 自动抓取点生成
- 自动碰撞规避
- 自动轨迹优化
- 自动软限位约束
- 自动安全认证级保护

这些能力需要在上位机层或扩展层显式补齐。

## 2. 当前项目的系统边界

当前仓库已经形成两层明确分工：

- `vendor/GALAXEA-A1Z`
  - 纯上游 SDK 镜像
  - 负责底层硬件/控制基础能力
- `a1z_ext`
  - 本地扩展层
  - 负责项目特有 backend、配置、server、Isaac 联动语义

这意味着后续所有“任务级”“抓取级”“仿真替身级”逻辑，应继续放在 `a1z_ext` 或新的本地包中，而不是回写到 `vendor`。

## 3. 当前可直接复用的能力

### 3.1 机器人基础控制

当前仓库已经具备：

- 关节位置命令
- 夹爪开合命令
- 关节状态读取
- mock backend
- Isaac Sim backend
- SocketCAN 真机 backend
- 基于 Unix socket 的控制服务封装

这部分已经足以支撑“任务执行器”去下发关节级动作。

### 3.2 模型与动力学基础

当前可复用能力包括：

- Pinocchio/重力模型
- 上游 SDK 自带逆运动学
- 项目侧控制 URDF 与 Isaac URDF 分离
- Isaac 中的可视化与联调环境

这部分足以支撑：

- 给定末端目标位姿，求一组候选关节解
- 做基础重力补偿/姿态保持
- 在仿真中验证关节控制链路

### 3.3 工程基础设施

当前仓库已经具备：

- 容器化 Isaac Sim 开发环境
- SDK 独立 Python 运行时
- mock/server/Isaac 的专项验证脚本
- 统一 CLI 控制入口

这意味着你不需要再从零搭环境隔离层，可以直接在现有工作区上构建任务系统。

## 4. 当前不具备、必须补齐的能力

如果目标是“给定一个位置，系统自主完成抓取”，当前 SDK 还不够，至少还缺以下几类能力。

### 4.1 任务输入规范

你需要定义明确的任务输入，而不是只接受一个裸位置。

建议最少包含：

- 目标位置 `x, y, z`
- 目标姿态或姿态约束
- 抓取模式
  - 顶抓
  - 侧抓
  - 沿法向接近
- 预抓取偏移
- 夹爪目标开口
- 位置容差和姿态容差
- 执行超时时间

如果只有位置没有姿态，逆运动学通常会出现多解、奇异姿态或夹爪朝向错误的问题。

### 4.2 坐标系与标定链

你必须明确以下坐标关系，否则任务目标无法稳定落到机械臂控制坐标系：

- 世界坐标系
- 机器人基座坐标系
- 末端执行器坐标系
- 相机坐标系
- 目标物体坐标系

至少需要一条稳定的变换链：

- `world -> robot_base`
- `robot_base -> tool`
- 如果依赖视觉，还需要 `camera -> robot_base` 或 `camera -> world`

如果这部分不稳定，抓取任务即使 IK 能解出来，也会抓偏。

### 4.3 末端任务空间规划

当前 SDK 提供的是底层控制和 IK 基础，不等于完整抓取规划。

你需要补的任务空间能力包括：

- 预抓取位姿生成
- 接近轨迹生成
- 抓取闭合时机判定
- 撤离轨迹生成
- 失败重试策略

最少要形成一个有限状态机：

- Idle
- ReachPregrasp
- Approach
- CloseGripper
- Lift
- Retreat
- Done
- Failed

### 4.4 IK 结果筛选与约束层

这是当前最关键的缺口之一。

上游 SDK 的 IK 本体可用，但当前没有看到“完整任务级约束层”，尤其缺：

- 软限位约束
- 关节边界裕量
- 自碰撞约束
- 环境碰撞约束
- 连续性约束
- 奇异位姿回避
- 对当前姿态最近解的优先级策略

因此，不能把“IK 给出一个解”直接等价成“这个解可以安全执行”。

你至少需要自建一层 `IK solution filter`，负责：

- 限位检查
- 关节余量检查
- 与当前关节位置的距离排序
- 最大步长限制
- 末端姿态误差检查
- 速度/加速度可执行性检查

### 4.5 碰撞与环境约束

如果目标任务是真实抓取，仅靠 IK 不够。

还需要明确是否建设以下能力：

- 机械臂自碰撞检查
- 机械臂与桌面/支架/相机的碰撞检查
- 夹爪与目标以外物体的碰撞检查

如果短期不做完整在线碰撞规划，也至少应做：

- 静态禁入区
- 工作空间包围盒
- 桌面高度阈值
- 相机/支架保护区

### 4.6 夹爪抓取语义

当前系统有夹爪控制，但还没有形成任务语义层。

你需要定义：

- 抓取前默认开口
- 闭合速度/闭合模式
- 闭合完成判定
- 抓稳判定
- 抓取失败判定
- 放置时释放策略

如果夹爪没有力反馈闭环，就要明确采用什么近似判定：

- 时间判定
- 行程判定
- 开口变化阈值

### 4.7 执行监管与异常恢复

要把系统用于上位机任务执行，必须补执行监管层。

至少包括：

- 命令超时
- 后端断连检测
- 轨迹执行中断
- 到位失败
- 夹爪失败
- IK 无解
- 目标超出工作空间

系统必须把这些错误显式提升为任务状态，而不是只停留在底层日志。

## 5. 推荐的系统分层

建议按下面的结构建设，而不是把任务逻辑直接堆进 CLI 或脚本。

### 5.1 Driver Adapter Layer

职责：

- 封装真实后端、mock 后端、Isaac 后端
- 暴露统一机器人接口
- 屏蔽底层总线、socket、仿真差异

建议位置：

- `a1z_ext` 内继续扩展

### 5.2 Robot Service Layer

职责：

- 统一状态读取
- 统一动作下发
- 提供关节命令、末端命令、夹爪命令
- 统一错误码和健康状态

这是任务系统唯一允许依赖的机器人入口。

### 5.3 Kinematics And Constraints Layer

职责：

- 逆运动学求解
- 解筛选
- 限位检查
- 工作空间检查
- 姿态约束
- 连续性约束

这一层应该独立于任务状态机，保持纯算法语义。

### 5.4 Motion Generation Layer

职责：

- 预抓取/接近/撤离轨迹生成
- 关节插值
- 分段目标生成
- 速度与节拍控制

如果暂时不接入完整规划器，这一层至少要能做：

- 笛卡尔阶段分解
- 关节空间插值
- 分段执行

### 5.5 Task Execution Layer

职责：

- 管理抓取任务状态机
- 调用感知、IK、轨迹和执行层
- 汇总任务成功/失败原因

### 5.6 Perception / World Model Layer

职责：

- 接收目标位置来源
- 管理坐标转换
- 维护环境约束

即使当前不做完整视觉，也建议把“目标位置来源”和“环境模型”独立出来，不要直接在任务执行器里硬编码。

## 6. 推荐技术栈

以下是当前项目最合理的技术栈边界。

### 6.1 语言与运行时

- Python 3.11
- Isaac Sim 5.1 容器环境
- 独立 SDK venv

理由：

- 当前仓库已经围绕这一栈搭好
- SDK、Isaac、Pinocchio 兼容路径已存在
- 不需要再引入第二套主运行时

### 6.2 数值与机器人学

- `numpy`
- `pinocchio`
- 上游 `a1z` SDK 的动力学/IK能力

可选补充：

- `scipy` 用于数值优化或插值

### 6.3 通信与进程边界

建议保留当前模式：

- 机器人服务层通过本地 Python API 驱动
- 外部调用通过 Unix socket / JSON 控制面进入

如果后续需要上位机与下位机隔离更彻底，可以扩展为：

- 进程内机器人服务
- 进程外任务调度器
- 明确 RPC/消息协议

但不建议一开始就引入过重中间件。

### 6.4 仿真与验证

- Isaac Sim 作为几何与行为验证环境
- mock backend 作为快速离线接口验证环境

推荐策略：

- 算法联调优先 mock
- 几何验证优先 Isaac
- 最后再切换真机

### 6.5 可选中间件

如果未来要对接外部视觉、上位机 UI、任务编排，可考虑：

- ROS 2 作为系统集成层
- 但不要让 ROS 2 成为控制闭环的硬依赖

建议原则：

- 控制闭环核心保持 Python 本地可运行
- ROS 2 只承担集成、消息分发、生态对接

## 7. 任务输入与输出规范建议

### 7.1 输入规范

建议定义统一任务对象，例如：

- `task_id`
- `target_frame`
- `target_position`
- `target_orientation`
- `approach_vector`
- `pregrasp_offset`
- `gripper_opening`
- `tolerance_position`
- `tolerance_orientation`
- `timeout`
- `metadata`

### 7.2 输出规范

任务执行结果不应只返回成功或失败。

应至少包含：

- `status`
  - success
  - failed
  - aborted
  - timeout
- `failure_reason`
- `final_joint_state`
- `final_tool_pose`
- `gripper_state`
- `attempt_count`
- `timing_breakdown`

### 7.3 中间状态规范

建议统一阶段事件：

- task_received
- ik_started
- ik_failed
- plan_generated
- move_started
- pregrasp_reached
- approach_reached
- gripper_closed
- lift_completed
- task_completed
- task_failed

## 8. 安全与约束规范

### 8.1 必须具备的基础安全约束

即使不做工业级安全，也至少应建设：

- 关节硬限位检查
- 软裕量检查
- 最大单步关节变化限制
- 最大目标高度/最小目标高度限制
- 末端禁入区
- 夹爪动作前提检查

### 8.2 真机与仿真的语义对齐

如果 Isaac 要作为真机替身，必须保证以下语义一致：

- 关节顺序一致
- 关节符号一致
- 零位定义一致
- 夹爪开口归一化一致
- 控制频率量级一致
- 任务状态机一致

否则仿真验证结果不能外推到真机。

### 8.3 不能默认相信的能力

当前不得默认相信以下结论：

- IK 有解就一定可执行
- 末端到位就一定能抓住
- Isaac 中不碰撞就一定真机不碰撞
- 夹爪闭合就一定抓稳

这些都需要上位层独立判定。

## 9. 分阶段交付建议

### 阶段 1：控制闭环打通

目标：

- 给定关节目标可稳定执行
- 夹爪可稳定控制
- mock / Isaac / 真机接口语义统一

验收重点：

- 后端抽象一致性
- 状态读取一致性
- 错误处理一致性

### 阶段 2：末端位姿驱动

目标：

- 给定末端目标位姿，可求解 IK 并执行

验收重点：

- 无解判定
- 解筛选可靠性
- 关节限位与连续性检查

### 阶段 3：抓取状态机

目标：

- 形成 pregrasp -> approach -> close -> lift -> retreat 的完整任务流

验收重点：

- 阶段切换条件
- 失败回退策略
- 超时和中断处理

### 阶段 4：环境约束与视觉接入

目标：

- 目标位置来自外部世界模型或视觉模块
- 坐标链稳定
- 环境约束进入执行判定

验收重点：

- 标定稳定性
- 世界坐标系一致性
- 误差预算可解释

## 10. 当前项目建议补充的模块清单

为了真正完成“通过 SDK 驱动机械臂完成抓取任务”，建议新增以下本地模块：

- `a1z_ext/task/`
  - 任务状态机
  - 任务对象定义
  - 执行结果定义
- `a1z_ext/kinematics/`
  - IK 封装
  - IK 结果筛选器
  - 工作空间与约束检查
- `a1z_ext/motion/`
  - 预抓取/接近/撤离段生成
  - 关节插值器
- `a1z_ext/world/`
  - 坐标变换
  - 环境约束
  - 目标定义
- `a1z_ext/safety/`
  - 限位裕量
  - 禁入区
  - 目标合法性检查
- `a1z_ext/interfaces/`
  - 统一任务 API
  - 外部系统调用入口

## 11. 验证标准

最终系统至少应能回答下面这些问题，并且答案是可验证的：

- 输入的目标坐标属于哪个坐标系
- 当前使用的 IK 解为什么被选中
- 为什么判定该目标可达或不可达
- 为什么允许或拒绝执行该抓取
- 夹爪何时开始闭合
- 抓取成功或失败依据是什么
- 失败后系统为什么停止或重试
- Isaac 与真机的差异在哪里

如果系统不能清楚回答这些问题，说明它还不是一个可维护的任务执行系统，只是若干控制脚本的拼接。

## 12. 结论

基于当前仓库，直接用 SDK 做“关节控制、夹爪控制、仿真联调、基础 IK 求解”已经可行。

但如果目标是“给定一个位置，系统稳定完成抓取任务”，还必须补齐以下核心层：

- 任务输入规范
- 坐标系与标定链
- IK 约束与解筛选
- 任务空间运动分解
- 抓取状态机
- 夹爪任务语义
- 安全与异常恢复

简化地说：

- 当前 SDK 解决的是“怎么控制机械臂”
- 你还需要补的是“什么时候这样控制、为什么这样控制、控制失败后怎么办”

只有把后者补齐，这个项目才真正具备“上位机任务执行系统”的完整语义。
